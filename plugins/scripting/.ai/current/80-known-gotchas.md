## G1. `IR_EXTERNAL_DECLARATION_STUB` on `@InlineOnly` members in snippet `$$eval` — **FIXED 2026-05-18** (via G11 umbrella fix)

- **Symptom (historical)**: `Unhandled intrinsic in ExpressionCodegen: FUN IR_EXTERNAL_DECLARATION_STUB ... [inline]`. Triggers most often on `kotlin.collections.MutableMap.set` (`bindings[k] = v`), `kotlin.let`, `kotlin.also`, `kotlin.apply`, `kotlin.takeIf`, `joinToString$default`, and other `@InlineOnly` / default-arg-bearing stdlib operators.
- **Cause (historical)**: special case of G11 (parent-shape: `IrExternalPackageFragment` parent fails the codegen `require(callee.parent is IrClass)`). The earlier framing as an inliner-gap was a *secondary* concern (body not materialised) — the proximate exception is the parent shape.
- **Fix**: G11 fix in `ReplSnippetsToClassesLowering` (see G11 entry below) rewrites `IrExternalPackageFragment` parents to JVM file-class facades **before** codegen runs. `@InlineOnly` calls now lower normally for the REPL JVM path.
- **Generator workarounds remain valid as defensive coding**: `bindings.put(k, v)` over `bindings[k] = v` etc. — these never relied on the codegen fix, are slightly more conservative, and avoid re-introducing the issue if the EPPL-equivalent pass is ever removed or bypassed.
- **Reference**: [iterations/2026-05-17_bindings-partial.md](../iterations/2026-05-17_bindings-partial.md#key-learnings) (initial discovery, `MutableMap.set` workaround), [iterations/2026-05-18_jsr223-followup-1.md](../iterations/2026-05-18_jsr223-followup-1.md#key-learnings) (`?.let`/`?.also`/`?.apply`/`?.takeIf` confirmation), [iterations/2026-05-18_step1b-rootcause-refinement.md](../iterations/2026-05-18_step1b-rootcause-refinement.md) (G11 umbrella refinement), [iterations/2026-05-18_step1b-fix-landed.md](../iterations/2026-05-18_step1b-fix-landed.md) (production fix landed).

## G2. `[fake_override]` on cross-module REPL symbols — **FIXED 2026-05-18** (via G11 umbrella fix)

- **Symptom (historical)**: `IR_EXTERNAL_DECLARATION_STUB` failure where the IR call target is marked `[fake_override]` — e.g. `ReplState.put`, `ReplState.get`, sometimes `kotlin.Result.value`.
- **Cause (historical)**: special case of G11 — the fake-override callable still has `IrExternalPackageFragment` as parent because the inherited member's source is the external (deserialised) declaring class's file-class. Same proximate codegen require failure as G1.
- **Fix**: G11 fix in `ReplSnippetsToClassesLowering` reparents the callee onto a synthesised JVM file-class facade. `[fake_override]` calls (including inherited `ReplState.put` / `ReplState.get` paths) now reach codegen with `callee.parent is IrClass`.
- **Generator workarounds remain valid as defensive coding**: prefer direct `bindings.put(...)` / `bindings.get(...)` over a `ReplState` indirection — same defensive rationale as G1.
- **Reference**: [iterations/2026-05-18_jsr223-followup-1.md](../iterations/2026-05-18_jsr223-followup-1.md#remaining-9-failures-after-this-iteration), [iterations/2026-05-18_step1b-rootcause-refinement.md](../iterations/2026-05-18_step1b-rootcause-refinement.md) (refinement / partial retraction), [iterations/2026-05-18_step1b-fix-landed.md](../iterations/2026-05-18_step1b-fix-landed.md) (production fix landed).

## G3. `JvmDependencyFromClassLoader` is invisible to K2 FIR

- **Symptom**: types loaded only via the host classloader (test-`HashMap` subclasses, JSR-223 bindings types, implicit receivers from `getScriptContext`) resolve to nothing during FIR analysis — `UnresolvedSymbol` / `UNRESOLVED_REFERENCE`.
- **Cause**: K1 used `PackageFragmentFromClassLoaderProviderExtension` (K1-only legacy EP) to materialise classloader-only deps into descriptors. K2's FIR session does **not** see `JvmDependencyFromClassLoader` directly — it only consumes file-system jars/dirs in `dependencies`.
- **Workaround**: pre-extract a classpath with `scriptCompilationClasspathFromContext(classLoader, wholeClasspath = true, unpackJarCollections = true)` and feed it into `dependencies` as ordinary jars/dirs. Already wired in `K2ReplCompiler` (eager classpath extraction landed in commit `54cd2163`).
- **Reference**: [iterations/2026-05-17_bindings-partial.md](../iterations/2026-05-17_bindings-partial.md#key-learnings).

## G4. `LinkedSnippet` chain is producer-driven, consumer-walk

- **Symptom**: `NoClassDefFoundError` for classes the compiler clearly emitted (e.g. `ReplState` defined in synthetic snippet not visible at user snippet eval time); silent drops when the compiler appends N snippets but the evaluator only sees 1.
- **Cause**: K2 REPL compiler appends synthetic + user snippets onto the `LinkedSnippet` chain and returns the tail. Tail-only evaluation skips intermediate nodes.
- **Workaround**: `K2ReplEvaluator.eval()` walks the chain back from tail to `lastEvaluatedSnippet` and evaluates pending nodes in order. Don't bypass this walk if you add a new entry point.
- **Reference**: [iterations/2026-05-17_bindings-partial.md](../iterations/2026-05-17_bindings-partial.md#key-learnings).

## G5. Compiled-snippet `resultField` metadata can disagree with bytecode

- **Symptom**: `NoSuchFieldException: resN` in the evaluator after compilation succeeds.
- **Cause**: snippets that the compiler marks with `resultField("")` (e.g. synthetic snippets, statement-only forms) still ship metadata that the strict reflective lookup path picks up.
- **Workaround**: use lenient `runCatching { getDeclaredField(...) }` in the evaluator's result-field lookup. Already in place in `K2ReplEvaluator.evalSnippet()`.
- **Reference**: [iterations/2026-05-17_bindings-partial.md](../iterations/2026-05-17_bindings-partial.md#changes).

## G6. `getCurrentState(getContext())`, not `getCurrentState(context)` for `lineCounter`

- **Symptom**: snippet class-name collision (`snippet_0.repl.kts` produced twice); outer engine compiler's history conflicts with a custom-`ScriptContext`'s fresh state.
- **Cause**: when a caller passes a custom `ScriptContext` to `eval(String, Bindings)`, `getCurrentState(context)` produces a fresh state with `lineCounter = 0`, colliding with the outer compiler's history. The outer default-context state is the correct counter source — it co-ordinates with `replCompiler = getCurrentState(getContext()).compiler`.
- **Workaround**: always use `getCurrentState(getContext()).lineCounter++` on the engine's bookkeeping path. Custom-context bookkeeping flows through `lastScriptContext`, not through `getCurrentState`.
- **Reference**: [iterations/2026-05-18_jsr223-followup-1.md](../iterations/2026-05-18_jsr223-followup-1.md#key-learnings).

## G7. `val bindings` must be per-eval, not per-session

- **Symptom**: stale bindings on the second eval that uses a different `ScriptContext` (custom `Bindings`); NullPointerException-on-access for entries that exist in the new context.
- **Cause**: declaring `val bindings = getBindings(ENGINE_SCOPE)` only in the first synthetic snippet stores a static field capturing that eval's `ScriptContext`. Subsequent evals with a different `ScriptContext` see the stale field.
- **Workaround**: declare `val bindings` in **every** synthetic snippet so each property getter references its own class's `bindings` field, set from the `ScriptContext` active at that eval's `$$eval` invocation. Declare top-level eval helpers (`fun eval(String)`, `fun eval(String, Bindings)`) only in the first synthetic snippet.
- **Reference**: [iterations/2026-05-18_jsr223-followup-1.md](../iterations/2026-05-18_jsr223-followup-1.md#key-learnings).

## G8. JVM identifier constraints block `\`-based binding-name escaping — **RESOLVED 2026-07-01e, refined 2026-07-02, marker alphabet refined again 2026-07-02b** (marker encoding narrowed; backtick + delegate for everything else; marker alphabet is now a uniform hex code-point)

- **Symptom (historical)**: `testEvalWithContextNamesWithSymbols` fails — any `\`-escaped binding identifier (the K1 contract used `\,` for `.`, `\!` for `:`, etc.) is rejected by `FirJvmNamesChecker.INVALID_CHARS`.
- **Cause**: `FirJvmNamesChecker.INVALID_CHARS` includes `\` along with `.`, `:`, `;`, `[`, `]`, `/`, `<`, `>`. There is no JVM-safe escape using backslash. Underscore-only fallbacks hit "Names `_`, `__`, `___`, ... are reserved" parser rule.
- **Fix (Q14, 2026-07-01e prototype — superseded in scope by 2026-07-02, see below)**: the first prototype routed *every* non-plain-identifier name through a reversible plain-identifier `__<mnemonic>__` marker (`a.b` → `a__dot__b`, `c:d` → `c__colon__d`, `☺` → `__u263a__`; unmapped chars → `u<hex>`). Markers start with `_` but contain letters, so they dodge the reserved all-underscore rule; the getter/setter still reaches the value via the raw binding key (`bindings["a.b"]`), so only injectivity — not runtime decode — is required.
- **Fix (Q14, 2026-07-02 refinement)**: marker encoding is only *actually required* for the JVM-hard-invalid chars (`. ; [ ] / < > : \`, plus backtick/newline, none of which survive even backtick-quoting) — see **G12** for why the marker-only prototype over-applied to every other character. `encodeBindingNameToKotlinIdentifier` now backtick-quotes every other name (space, `$`, non-ASCII, JVM-"dangerous" `? * " | %`) **verbatim**, and `generateBindingSnippetIfNeeded` declares those properties with a generated `__Jsr223BindingDelegate` (`by ...`) instead of a hardcoded `get()`/`set()` — see G12 for why the delegate is required.
- **Fix (Q14, 2026-07-02b refinement — marker alphabet)**: the user asked for a more "well-known" alphabet than the hand-picked mnemonic words. HTML5 named character references were researched (`&period;`, `&colon;`, `&semi;`, `&lsqb;`/`&rsqb;`, `&sol;`, `&bsol;`, `&lt;`, `&gt;` all exist) but don't cover every marker-needing character (no name for backtick or raw newline/CR), and a literal numeric-escape style (`&#46;` / `%2E`) can't be embedded directly since it reintroduces other problematic characters (`&`, `#`, `;`, `%`). Chosen instead: `BINDING_NAME_CHAR_MNEMONICS` was removed entirely; `encodeBindingNameToMarkerIdentifier` now uniformly encodes *every* marker-needing character as `__u<hex>__` (its Unicode code point in hex) — the same rule the fallback branch already used for characters with no mnemonic entry (e.g. `☺` → `__u263a__`), now the *only* rule (`a.b` → `a__u002e__b`, `c:d` → `c__u003a__d`). A literal `\uXXXX`-style escape (with a real backslash) is impossible, since `\` is itself one of the marker-needing characters — reusing it would just reintroduce the very character the scheme exists to eliminate.
- **Companion gotcha — `Name.isValidIdentifier` is a JVM-spec check, NOT a Kotlin-identifier check**: it returns `false` only for `. ; [ /` (and a leading `<`), so it accepts JVM-legal-but-non-Kotlin names like `o]p`, `g$h`, `c:d`, `i<j`, `k>l`, `☺` and space. Using it as a "clean identifier?" gate emitted those **raw** as property names → `var <no name provided>` parse errors (and/or `FirJvmNamesChecker`). Use a real plain-Kotlin-identifier check (ASCII letters/digits/`_`, no leading digit, not all-underscore) when deciding whether a name can be emitted verbatim.
- **Status**: **resolved** — see `Q14` in [`../target/90-open-questions.md`](../target/90-open-questions.md). Contract note: this is a K1 → K2 user-visible name change for the hard-invalid subset only (`` `a\,b` `` → `a__u002e__b`); every other previously-K1-backtick-quoted name (`` `g$h` ``, `` `u v` ``, `` `☺` ``) keeps its original K1 spelling, now backed by a delegate instead of a hardcoded accessor.
- **Reference**: [iterations/2026-07-02b_jsr223-binding-name-uniform-codepoint-marker.md](../iterations/2026-07-02b_jsr223-binding-name-uniform-codepoint-marker.md) (marker-alphabet refinement); [iterations/2026-07-02_jsr223-binding-name-delegate-fix.md](../iterations/2026-07-02_jsr223-binding-name-delegate-fix.md) (marker/backtick-split refinement); [iterations/2026-07-01e_jsr223-binding-name-encoding.md](../iterations/2026-07-01e_jsr223-binding-name-encoding.md) (superseded-in-scope prototype); (historical) [iterations/2026-05-18_jsr223-followup-1.md](../iterations/2026-05-18_jsr223-followup-1.md#key-learnings).

## G9. Lambda binding types have non-parseable `qualifiedName`

- **Symptom**: synthetic snippet emits e.g. `var myFun: Foo$$Lambda$1` and parser fails with "Property getter or setter expected" + cascading parse errors. Common under `-Xlambdas=indy`.
- **Cause**: indy-lambdas and other local/anonymous classes have a non-null `KClass.qualifiedName` on some JDKs (`Foo$$Lambda$1`, `MyKt$f$lambda$1`, names with `/` or `<`), but that string is not a valid Kotlin type reference.
- **Workaround**: filter such bindings in the generator with `isParseableKotlinQualifiedName(qn)` (dot-separated chain of valid Kotlin identifiers). Filtered bindings remain accessible via `bindings["..."]` from user code, just not as auto-generated typed properties. Landed in `propertiesFromContext.kt` (iteration 2026-05-18 follow-up).
- **Status**: see `Q15` in [`../target/90-open-questions.md`](../target/90-open-questions.md) for a typed-access design option (functional-interface synthesis vs erased `Any?` accessor).
- **Reference**: [iterations/2026-05-18_jsr223-followup-1.md](../iterations/2026-05-18_jsr223-followup-1.md#remaining-9-failures-after-this-iteration) + this session's follow-up.

## G10. K2 JSR-223 implicit receiver is `ScriptContext`, not `ScriptTemplateWithBindings` — **FIXED 2026-07-02c** (second implicit receiver)

- **Symptom (historical)**: user-defined `fun ScriptTemplateWithBindings.foo(...)` is unreachable from a subsequent snippet: "Candidate ... is inapplicable because of a receiver type mismatch".
- **Cause**: K1 path exposed bindings via helpers receiving `ScriptTemplateWithBindings`. The K2 path uses only `ScriptContext` as the implicit receiver of `$$eval`. Architectural divergence between the two paths.
- **Fix**: `ScriptTemplateWithBindings` is now added as a **second** implicit receiver alongside `ScriptContext` — both `configureExposedJsr223Context` overloads in `libraries/scripting/jvm-host/src/.../jsr223/propertiesFromContext.kt` add it idempotently (compile-time) / pass a `Jsr223ScriptTemplateWithBindings` wrapper instance (eval-time) around the same live engine-scope `Bindings`. No FIR/IR/evaluator change needed — the whole implicit-receiver pipeline was already N-ary. `testEvalInEvalWithBindingsWithLambda` is un-`@Disabled` and passes; no receiver-ambiguity diagnostics observed.
- **Status**: **resolved** — see `Q16` in [`../target/90-open-questions.md`](../target/90-open-questions.md) (JSR-223 K2 implicit-receiver strategy).
- **Follow-up regression, since fixed**: this fix's original implementation hoisted the receiver-class list to a top-level property, which regressed plain (non-JSR-223) `.main.kts` compilation with a `NoClassDefFoundError: javax/script/ScriptContext` — see **G14**.
- **Reference**: this session's investigation of `testEvalInEvalWithBindingsWithLambda`; fix landed same session (2026-07-02c).

## G11. `IR_EXTERNAL_DECLARATION_STUB` on *any* external Kotlin top-level decl referenced from a snippet (umbrella over G1/G2) — **FIXED 2026-05-18** (migration step 1b)

- **Symptom (historical)**: `java.lang.IllegalArgumentException: Unhandled intrinsic in ExpressionCodegen: FUN IR_EXTERNAL_DECLARATION_STUB name:<X> ...` thrown from `org.jetbrains.kotlin.backend.jvm.codegen.ExpressionCodegen.visitCall` at line 519 during JVM bytecode generation for a snippet's `$$eval` body. `<X>` is any callable resolved against an external module: regular top-level `val`/`fun`, `@InlineOnly` stdlib operator, fake-override on a cross-module class — they all funnel into the same failure.
- **Proximate failure point**: `compiler/ir/backend.jvm/codegen/src/.../ExpressionCodegen.kt:519` — `require(callee.parent is IrClass) { "Unhandled intrinsic in ExpressionCodegen: ${callee.render()}" }`. The require fires whenever an `IrCall` survives all lowerings pointing at an `IrSimpleFunction` whose `parent` is *not* an `IrClass`. For external Kotlin top-level decls, the parent set by `Fir2IrDeclarationStorage.findIrParent` is `IrExternalPackageFragment` (a package, not a class), and no JVM-pipeline lowering rewrites it into the equivalent JVM file-class for the REPL build.
- **Cause (mechanism)**: the K2 JVM `ExternalPackageParentPatcherLowering` is supposed to rewrite this exact parent shape for the *currently-lowered* file, but it never visits the snippet `targetClass` in the REPL pipeline (the snippet's class is structurally hidden by `IrReplSnippet` / `ReplSnippetsToClassesLowering` removal sequencing). Even if it did, the standard JVM `FileClassLowering` pass operates on the *current* module's top-level decls only, not on referenced external decls. For source-form symbols (IDE / `allowNonCachedDeclarations` mode) `Fir2IrDeclarationStorage` at `Fir2IrDeclarationStorage.kt:1390-1427` synthesises a non-cached file-class facade — but that branch never fires in the production REPL compile.
- **Fix landed 2026-05-18 (migration step 1b)**: added a REPL-scoped EPPL-equivalent post-pass — `ReplSnippetExternalPackageParentPatcher` inside `ReplSnippetsToClassesLowering` (`plugins/scripting/scripting-compiler/src/.../irLowerings/ReplSnippetLowering.kt`). It mirrors `org.jetbrains.kotlin.backend.jvm.lower.ExternalPackageParentPatcherLowering.Visitor.visitMemberAccess`: for every `IrMemberAccessExpression` whose callee implements `IrMemberWithContainerSource`, has a `FacadeClassSource` container, and is currently parented on `IrExternalPackageFragment`, it builds a JVM file-class facade via `createJvmFileFacadeClass` + `classNameOverride` and reparents the callee (and corresponding property, if any) on the facade. The pass runs eagerly on each snippet's `targetClass` after `finalizeReplSnippetClass`, so the snippet body's IR is rewritten before any later JVM lowering observes the package parent. Bytecode references the real `*Kt` (or multifile-facade) class on the classpath, matching what normal `.kt` compilation emits.
- **Verification**: JSR-223 suite went from 12 PASS / 6 SKIP / 3 FAIL (baseline) to 17 PASS / 1 SKIP / 3 FAIL. 5 of the 6 BLOCKED-CODEGEN tests now pass: `testResolveFromContextStandard` (plain external `val`), `testResolveFromContextLambda` (`@InlineOnly` `inlineCallLambda` + `callLambda`), `testResolveFromContextDirectExperimental` (classloader-backed plain external `val`), `testMultipleCompilable` (`joinToString$default`), `testEvalWithContext` (`bindings["nullable"]?.let { ... }`). The 6th (`testEvalWithContextDirect`) now fails for a different, non-codegen reason (synthetic-snippet null-binding type bug — see Q17). The 3 remaining failures are pre-existing Q14 / Q15 / Q16 design issues, unchanged.
- **Reference**: [iterations/2026-05-18_step1b-fix-landed.md](../iterations/2026-05-18_step1b-fix-landed.md) (this iteration — fix landed + verification), [iterations/2026-05-18_step1b-rootcause-refinement.md](../iterations/2026-05-18_step1b-rootcause-refinement.md) (root-cause refinement, second iteration), [iterations/2026-05-18_codegen-stub-investigation.md](../iterations/2026-05-18_codegen-stub-investigation.md) (initial investigation, first iteration).

## G12. Backtick-quoted-property + `getBindings(...)`-call in the same live REPL snippet trips "Property getter or setter expected" — **WORKAROUND landed 2026-07-02** (delegated properties)

- **Symptom**: a synthetic bindings snippet declaring a backtick-quoted property with a hand-written `get()`/`set()` body (e.g. `` var `u v`: Int / get() = ... / set(value) { ... } ``) fails to compile with `error: Property getter or setter expected`, even though the identical declaration compiles fine as a plain, standalone `.kts` file.
- **Cause**: `parseProperty(DeclarationParsingMode.SCRIPT_TOPLEVEL)` in `compiler/psi/parser/src/.../parsing/KotlinParsing.java` (mirrored in `compiler/multiplatform-parsing/.../KotlinParsing.kt` for the K2 light-tree front end) parses accessor blocks via a newline/semicolon **heuristic** (`myBuilder.newlineBeforeCurrentToken()`), not a keyword — this is the same statement-boundary ambiguity class that `DeclarationParsingMode.LOCAL` normally sidesteps by disabling accessors outright (`accessorsAllowed = false`); `SCRIPT_TOPLEVEL` is the one statement-sequence mode that still turns accessors on. Reproduction narrowed the trigger to the **live, incremental REPL/JSR-223 pipeline specifically**: a snippet containing both (a) a call resolved through the REPL's implicit-receiver machinery (the snippet's own `val bindings = getBindings(...)`) and (b) a backtick-quoted property with a hand-written accessor body, in the *same* snippet, misfires this heuristic. An equivalent one-shot `dist/kotlinc -script` compile of the same source (same backtick property + accessor text, no REPL session) does **not** reproduce it — so the extra ingredient is something about incremental-REPL-session compilation state, not the backtick name, the accessor syntax, or the implicit-receiver call in isolation. The exact incremental-vs-one-shot state difference that flips the heuristic was not pinned down further (would need debugger instrumentation of the live REPL compiler at the `errorUntil` call site).
- **Workaround**: don't emit a hardcoded `get()`/`set()` body for a backtick-quoted property in this generator. Declare it with a delegate (`by ...`) instead — a delegate expression is consumed by `parsePropertyDelegateOrAssignment()` *before* the accessor-parsing block runs at all, so the misfiring heuristic is never reached for these properties. Landed as `__Jsr223BindingDelegate` (a generated `getValue`/`setValue` class emitted once per synthetic-snippet chain) in `libraries/scripting/jvm-host/src/.../jsr223/propertiesFromContext.kt`; see G8 for the companion binding-name-encoding change this enabled (backtick-quoting instead of marker-encoding for most special characters).
- **Reference**: [iterations/2026-07-02_jsr223-binding-name-delegate-fix.md](../iterations/2026-07-02_jsr223-binding-name-delegate-fix.md).

## G13. `K2ReplCompiler`'s per-snippet FIR session silently falls back to classpath-based script-definition rediscovery — **FIXED 2026-07-02d, root cause addressed at the naming source 2026-07-03, indirection removed 2026-07-03b**

- **Symptom**: for a `K2ReplCompiler` session whose template's `fileExtension` doesn't match the synthetic per-snippet source name pattern (e.g. `MainKtsScript`'s `main.kts` vs a snippet named `...repl.kts`), the session's own compile-time refinements (e.g. JSR-223's implicit receivers) are silently dropped — e.g. `Unresolved reference 'getBindings'` on the very first auto-generated line of a synthetic bindings snippet, for **every** snippet in the session, not just an edge case.
- **Cause**: unlike the one-shot `ScriptJvmK2CompilerImpl` (which registers both a `FirScriptCompilationComponent` bound to `state.hostConfiguration` *and* pre-seeds `scriptRefinedCompilationConfigurationsCache` for the FIR session), `K2ReplCompiler.createCompilationState` never registered a `session.scriptCompilationComponent`, nor set `compilerConfiguration.scriptingHostConfiguration`. So `FirScriptDefinitionProviderService.hostConfiguration` always fell through to a **freshly, independently built** `defaultHostConfiguration` (via `FirScriptDefinitionProviderService.getFactory(compilerConfiguration)`'s classpath-discovery branch), never the REPL session's own correctly-wired `hostConfiguration`/`scriptCompilationConfiguration`. On top of that, even the REPL session's own definition (`ScriptDefinition.FromConfigurations`, registered in `K2ScriptingCompilerEnvironment.createCompilerState` — a *different*, not-actually-used-by-`K2ReplCompiler` bootstrap path) matches sources by `fileExtension`, so a synthetic snippet name that doesn't share the template's extension falls through *all* registered/classpath-rediscovered definitions to the generic, host-configuration-less `ScriptTemplateWithArgs`-based default — carrying none of the session's wiring.
- **Fix (2026-07-02d, superseded)**: `K2ReplCompiler.createCompilationState` now builds and registers its own `CliScriptDefinitionProvider`/`scriptCompilationConfigurationProvider` (mirroring the pattern already used by `K2ScriptingCompilerEnvironment.createCompilerState`), and both call sites used a `ReplSessionScriptDefinition` (`K2ScriptingCompilerEnvironment.kt`) whose `isScript` always returned `true` — bypassing extension-based matching entirely rather than fixing the mismatch.
- **Fix (2026-07-03, root cause)**: the always-`true` `isScript` override hijacked the script-definition-matching contract instead of fixing the actual mismatch. Root-caused to the snippet *file name generation* side instead: `KotlinJsr223ScriptEngineImpl.compile()` hard-coded the synthetic snippet name's suffix as `.repl.kts`, regardless of the host template's own `fileExtension` (e.g. `main.kts`). Changed it to suffix `.repl.<fileExtension>` (read from the session's `ScriptCompilationConfiguration.fileExtension`, e.g. `snippet_0.repl.main.kts` for `MainKtsScript`, unchanged `snippet_0.repl.kts` for the default `kts` extension). The JSR-223 synthetic-bindings-snippet name (`generateBindingSnippetIfNeeded` in `propertiesFromContext.kt`) is prefixed onto the main snippet's own name, so it inherits the corrected extension automatically. With snippet names always ending in the template's own extension, the standard `ScriptDefinition.FromConfigurationsBase.isScript` extension check matches correctly again — the `ReplSessionScriptDefinition` override is no longer needed and was removed; both call sites now register a plain `ScriptDefinition.FromConfigurations(hostConfiguration, compilationConfiguration, null)`.
- **Fix (2026-07-03b, indirection removed)**: even after the naming fix, `K2ReplCompiler.createCompilationState` still fed its correctly-wired `hostConfigurationWithProvider` to `FirScriptDefinitionProviderService` *indirectly*, by stashing it in the shared, mutable `compilerConfiguration.scriptingHostConfiguration` and relying on `FirScriptDefinitionProviderService`'s own lazily-cached `defaultHostConfiguration` fallback (`getFactory(compilerConfiguration)`) to read it back later. `ScriptJvmK2CompilerImpl` never needed this indirection — it registers a `FirScriptCompilationComponent` directly on each compiled FIR session via `session.register(...)`, and `FirScriptDefinitionProviderService.hostConfiguration` always prefers `session.scriptCompilationComponent?.hostConfiguration` over its own fallback. `K2ReplCompiler.compileImpl` now does the same: right after `FirJvmSessionFactory.createSourceSession(...)`, it calls `session.register(FirScriptCompilationComponent::class, FirScriptCompilationComponent(state.hostConfiguration))`, and the `compilerConfiguration.scriptingHostConfiguration` assignment in `createCompilationState` was removed (it had no other reader in this file). Purely a wiring-mechanism simplification — same `hostConfigurationWithProvider` value, same `ScriptDefinition`/`CliScriptDefinitionProvider` construction, just plugged in directly instead of round-tripping through the shared `CompilerConfiguration`.
- **Diagnosis note**: this gotcha was easy to misattribute to "classpath rediscovery bypasses the JSR-223 host override" (the original hypothesis) — live debugging showed the rediscovered `MainKtsScript` definition doesn't even match the synthetic snippet source's extension, so it was never the one silently selected; the real defect was the *missing session component registration*, causing a fallback several levels further down (the generic default definition), not the rediscovered one.
- **Reference**: [iterations/2026-07-02d_jsr223-mainkts-bypass-rediscovery.md](../iterations/2026-07-02d_jsr223-mainkts-bypass-rediscovery.md) (original always-`true` workaround); superseding fix landed 2026-07-03 (snippet-naming root-cause fix); indirection removed 2026-07-03b (direct `FirScriptCompilationComponent` registration, this session).

## G14. Top-level `listOf(SomeClass::class, ...)` eagerly loads the referenced classes for *every* caller of the file, not just the JSR-223 branch — **FIXED 2026-07-02e**

- **Symptom**: plain, non-JSR-223 `.main.kts` scripts (e.g. `MainKtsIT.testCachedReflection`, `testCacheWithFileLocation`, run via the `kotlin` launcher / CLI, no JSR-223 engine involved) started failing to compile with `error: javax/script/ScriptContext (<script>.main.kts): java.lang.NoClassDefFoundError: javax/script/ScriptContext` after the G10 (Q16) second-implicit-receiver fix — even though such scripts never touch `ScriptContext` as a receiver.
- **Cause**: the G10 fix introduced `private val REQUIRED_IMPLICIT_RECEIVERS = listOf(ScriptContext::class, ScriptTemplateWithBindings::class)` as a **top-level property** in `propertiesFromContext.kt`, evaluated by the file-facade class's static initializer (`<clinit>`) the first time *any* top-level declaration in that file is touched. `MainKtsScriptDefinition` wires `beforeCompiling(::configureExposedJsr223Context)` **unconditionally**, regardless of whether the host is a JSR-223 engine — so merely referencing that function (even for the early-return, non-JSR-223 branch, which checks `jsr223.getScriptContext == null` and bails before ever needing a receiver) forced the class carrying `REQUIRED_IMPLICIT_RECEIVERS` to load, and with it `javax.script.ScriptContext`. In whatever restricted classpath/module context the plain-`main.kts` compile ran under, that JDK class wasn't resolvable, so the eager load failed with `NoClassDefFoundError` — turning an unrelated design change into a hard failure for scripts that never asked for JSR-223 semantics at all.
- **Fix**: moved the receiver list back to a local `val` computed *inside* `configureExposedJsr223Context`, **after** the `getScriptContext == null` early-return guard — mirroring how it worked before G10 (a single `ScriptContext::class` reference living only inside the guarded branch, so it's resolved lazily and only for actual JSR-223 usage). No behavior change for real JSR-223 usage; plain scripts once again never touch `javax.script.*` classes.
- **Lesson (general)**: a top-level `val`/`object` in Kotlin is eagerly initialized by the enclosing file/class's `<clinit>`, which runs on **first access to any member of that file/class** — not just first access to that specific property. Any `::class` reference (or other class-loading-triggering expression) placed in such a property leaks its class-loading cost to every caller of the file, even ones that never read that property. Prefer computing such values locally inside the function that actually needs them, especially when the function has an early-return branch meant to skip the corresponding work entirely.
- **Reference**: [iterations/2026-07-02e_jsr223-mainkts-fix-the-fix.md](../iterations/2026-07-02e_jsr223-mainkts-fix-the-fix.md).

## G15. `K2ReplCompiler`'s session-wide `isReplSnippetSource { _, _ -> true }` misclassifies light-tree-compiled REPL *imports* as snippets — **DEFERRED 2026-07-02f** (test muted, not fixed)

- **Symptom**: `MainKtsJsr223Test.testWithImport` fails with the LightTree "missing support" diagnostic (`TODO("KT-77583")` in `LightTreeRawFirDeclarationBuilder.convertReplSnippet`) as soon as the root REPL snippet does `@file:Import(...)` of another `.main.kts` file.
- **Investigation finding**: the root snippet is PSI-based (`KtFileScriptSource`, `buildFirFromKtFiles`), but `@file:Import`ed scripts are ordinary `FileScriptSource`s that never go through PSI parsing, so they're compiled via `buildFirViaLightTree` — this split is by design and mirrors the one-shot `ScriptJvmK2CompilerImpl` path for regular script imports, so it is **not** itself a bug. The actual bug: `AbstractRawFirBuilder.convertScriptOrSnippets` picks `convertScript` (implemented) vs `convertReplSnippet` (unimplemented, `TODO("KT-77583")`) via `isReplSnippet(script, sourceFile)`, which for the light-tree builders falls through to `FirReplSnippetConfiguratorExtensionImpl.isReplSnippetsSource`, which reads `hostConfiguration[ScriptingHostConfiguration.repl.isReplSnippetSource]`. `K2ReplCompiler.createCompilationState` registers this predicate once per session as `{ _, _ -> true }` — unconditionally `true` for **any** source compiled in that session, including light-tree-compiled imports that are plain scripts, not snippets. (`PsiRawFirBuilder` is unaffected — it overrides `isReplSnippet` to check the PSI `KtScript.isReplSnippet` flag directly, so the root snippet is unaffected by this predicate.) The one-shot `ScriptJvmK2CompilerImpl` path never sets `isReplSnippetSource` at all, so its light-tree-compiled imports correctly take `convertScript` and work.
- **Why this matters**: this means `testWithImport` could plausibly be fixed **without** waiting for full `KT-83498` light-tree-REPL-snippet support, by narrowing `isReplSnippetSource` in `K2ReplCompiler` to discriminate the actual root/main snippet source instead of blindly returning `true` for every source in the session.
- **Decision (2026-07-02f)**: explicitly deferred/ignored for now — no fix attempted. `MainKtsJsr223Test.testWithImport` is `@Ignore`d with a reference to this gotcha and to `Q2`/`KT-77583`/`KT-83498`, rather than left as an unexplained red failure.
- **Status**: **open, deferred by decision** — not to be rediscovered as "just KT-83498/light-tree-REPL-snippet support is missing" without first checking whether narrowing `isReplSnippetSource` alone would suffice.
- **Reference**: this session's investigation (root-caused via code tracing, not live debugging); see `Q2` in [`../target/90-open-questions.md`](../target/90-open-questions.md).
