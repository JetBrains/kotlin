# JSR-223 / stateless remote compilation — direct on-daemon `ScriptEngine` (no BTA) — 2026-07-03

## Overview

Per explicit direction: the BTA-backed `KotlinJsr223BtaScriptEngineImpl` (2026-07-02g) is difficult to embed into IntelliJ, where this JSR-223 functionality needs to be available. This iteration adds a **direct on-daemon** variant that talks to the Kotlin compile daemon straight through the daemon-client API (`CompilerId` / `KotlinCompilerRunnerUtils.newDaemonConnection` / `CompileService.compile`) instead of going through the Build Tools API, riding the daemon's regular compile path (now available via stateless snippet compilation) rather than adding any new daemon RMI interface.

## Workstream / Issue

JSR-223 K2 bindings (Option D) / stateless remote REPL compilation (Q5, transport). New deliverable built as a portable **example**, not a fix.

## Decisions made up front

1. **Module placement**: `libraries/examples/scripting/jsr223-daemon` (project `:examples:scripting-jsr223-daemon`), per explicit instruction — unlike `jsr223-bta` (`libraries/scripting/*`), this is meant to be copied wholesale into the IntelliJ repo later, so it lives under `examples`.
2. **No daemon interface changes**: the snippet rides a plain `CompileService.compile(...)` call switched into snippet mode by the existing scripting-plugin CLI options (`repl-snippet-mode` / `repl-snippet-name` / `repl-snippet-prior-artifact` / `repl-snippet-artifact-output`) — exactly the shape a CLI invocation already produces; only the transport (direct daemon-client call vs. BTA) differs from the K2/BTA implementations.
3. **Shape mirrors the K2/BTA implementation**: same `AbstractScriptEngine` + `Compilable` shape, same deferred-bindings scope (`$$eval` invoked with no arguments), same "not registered as a `javax.script.ScriptEngineFactory` service" choice, same artifact-replay reimplementation pattern (`DaemonReplSnippetSession`, analogous to `BtaReplSnippetSession`).

## What was built

- **`DaemonReplSnippetCompiler`** (`.../daemon/DaemonReplSnippetCompiler.kt`): builds the CLI-argument-shaped snippet-mode invocation (`-expression` + `plugin:kotlin.scripting:repl-snippet-*` options + prior-artifact/output files), connects to (or spawns) the compile daemon via `CompilerId.makeCompilerId(compilerClasspath)` + `KotlinCompilerRunnerUtils.newDaemonConnection(...)`, and drives a single non-incremental `CompileService.compile(...)` call with a small local no-op `CompilationResults` RMI stub (the real one is `internal`) and a `CollectingMessageCollector` that captures diagnostics as plain strings (used both for compile-failure reporting and for surfacing the underlying cause when the daemon connection itself fails).
- **`DaemonReplSnippetSession`** (`.../daemon/DaemonReplSnippetSession.kt`): decodes the wire artifact via the public `SnippetArtifactCodec`/`decodeHeader()`, defines its classes incrementally onto one shared classloader, reflectively invokes `$$eval` (hardcoded string literal, per `AGENT_INSTRUCTIONS.md`'s "don't rename/shadow" guidance), and returns the captured result field (or `null`). Essentially the same shape as `BtaReplSnippetSession`, duplicated rather than shared since the decode helpers it needs are `internal` to `:kotlin-scripting-compiler`.
- **`KotlinJsr223DaemonScriptEngineImpl` / `KotlinJsr223DaemonCompiledScript`** (`.../daemon/KotlinJsr223DaemonScriptEngineImpl.kt`): `AbstractScriptEngine` + `Compilable`; each `eval`/`compile` call compiles the snippet against all prior artifacts (accumulated per engine instance == per REPL session) and either runs it immediately or returns a `CompiledScript` wrapping the artifact for a later `eval()`.
- **`KotlinJsr223DaemonScriptEngineFactory`** (`.../daemon/KotlinJsr223DaemonScriptEngineFactory.kt`): the `KotlinJsr223JvmScriptEngineFactoryBase` subclass; takes the daemon's own compiler classpath, an additional (snippet-compile) classpath, daemon run/log dirs, and a shutdown-delay knob. Not registered as a `javax.script.ScriptEngineFactory` service.
- **`KotlinJsr223DaemonScriptEngineTest`** (`libraries/examples/scripting/jsr223-daemon/test/.../daemon/test/...`): 4 tests mirroring `KotlinJsr223BtaScriptEngineTest` exactly (simple eval, cross-snippet reference, separate compile-then-eval, declaration-only snippet → `null`), against a **real** compile daemon spawned by the direct daemon-client transport.
- **`build.gradle.kts`**: `api(:kotlin-scripting-jvm-host-unshaded)` + `implementation(:kotlin-compiler-runner-unshaded, :kotlin-daemon-client, :daemon-common, :kotlin-scripting-compiler)`; a dedicated `daemonCompilerClasspath` configuration (`:kotlin-compiler` + `:kotlin-daemon` + `:kotlin-scripting-compiler`) resolved and handed to the test JVM via a system property, so the daemon that gets spawned during tests is self-contained and plugin-discoverable without any shaded/relocated jar synthesis (unlike `jsr223-bta`, which needs its BTA impl's shaded jar).
- Registered the module in `settings.gradle.kts` (include + `projectDir`) and added it to the `notCacheableTestProjects` exemption list in `repo/gradle-build-conventions/buildsrc-compat/src/main/kotlin/common-configuration.gradle.kts`, and added `-Xallow-kotlin-package` to the module's `KotlinJvmCompile` tasks (package is `kotlin.script.experimental.jvmhost.jsr223.daemon`, mirroring the K2/BTA sibling packages).

## Bugs hit and fixed along the way

1. **Daemon fails to start — `ClassNotFoundException: org.jetbrains.kotlin.daemon.KotlinCompileDaemon`**: the plain `:kotlin-compiler` project jar does **not** bundle the daemon's own main class or `daemon-common`/`kotlin-daemon-client` — in `prepare/compiler/build.gradle.kts`, `:kotlin-daemon`/`:kotlin-daemon-client` are listed only under `distLibraryProjects` (copied as *separate* jars into `dist/kotlinc/lib/`), not `fatJarContents` (what actually gets baked into the compiler jar). Root-caused by pointing the daemon's log directory at a fixed, inspectable path (the default silently produced no log file at all, meaning the JVM never even started) and by having the connection-failure path surface the `CollectingMessageCollector`'s captured diagnostics instead of a bare `IllegalStateException`. Fixed by adding `project(":kotlin-daemon")` to the `daemonCompilerClasspath` configuration.

## Key Learnings

- A project's "compiler jar" and its "daemon-launchable classpath" are not the same thing in this repo: `:kotlin-compiler`'s own artifact never bundles `org.jetbrains.kotlin.daemon.KotlinCompileDaemon` — that only ships as the separate `:kotlin-daemon` (+ `:kotlin-daemon-client`) dist jars. Any direct (non-BTA, non-`dist/kotlinc`) daemon-client integration needs to assemble its own daemon-launch classpath explicitly from project jars — the BTA path sidesteps this because `kotlin-build-tools-impl`'s shaded jar already embeds everything.
- Silently-null `KotlinCompilerRunnerUtils.newDaemonConnection(...)` results are best debugged by (a) pointing `DaemonLogOptions.logsPath` at a fixed, inspectable directory to see whether the daemon JVM started at all, and (b) capturing the `MessageCollector` passed into the call and rendering its collected messages into the thrown exception — `newDaemonConnection` always reports through that collector on a `null` result, regardless of the `isDebugEnabled` flag.

## Addendum (same day): `-expression` → `-script <file>`, and a latent `compileReplSnippet` bug

Follow-up review flagged two problems with the original `-expression`-based invocation:

1. **CLI-argument quoting risk**: `-expression <source>` smuggles the whole snippet body through a single CLI argument string; a sufficiently pathological source could in principle be corrupted by a transport that is sensitive to quoting/whitespace/length.
2. **Wrong semantics**: `-expression` is *the* eval-a-string entry point; passing a snippet meant only to be *compiled* through it is misleading even though `REPL_SNIPPET_COMPILATION_MODE` short-circuits before any evaluation happens.

**Fix**: `DaemonReplSnippetCompiler` now writes the snippet source to a temp file named after the snippet itself and passes it via `-script <path>` instead of `-expression <source>`. Added `KotlinJsr223DaemonScriptEngineTest` cases exercising sources that are awkward to smuggle through a single CLI argument: embedded quotes/backslashes, `$`/backtick identifiers, triple-quoted multiline strings, unicode/emoji, and a longer multi-declaration snippet.

**Bug found and fixed by the new tests**: switching to `-script <file>` immediately broke *every* test (not just the new "hostile" ones) with `NoClassDefFoundError: com/intellij/openapi/vfs/LocalFileSystem`. Root cause was in shared plugin code, not this module: `compileReplSnippet` (`AbstractScriptEvaluationExtension.kt`) only re-wrapped the incoming `SourceCode` into a plain `StringScriptSource` when the caller's `repl-snippet-name` option *differed* from the source's own name (a guard against `-expression`'s always-`script.kts` naming). Since our temp file is now named exactly after the snippet, the names always matched, so the *original*, file/`VirtualFile`-backed `SourceCode` (from `scriptFile.toScriptSource()`) was passed straight into `K2ReplStatelessCompiler`, which needs a real IntelliJ `LocalFileSystem` to resolve a file-backed source — a class that is (by design) never on the bare CLI/daemon classpath. Fixed by making `compileReplSnippet` **always** re-wrap into a `StringScriptSource(snippet.text, explicitName ?: snippet.name)`, regardless of whether the name already matches — `K2ReplStatelessCompiler` only ever needs the text and a name, never a real file/VFS handle. This is a fix to shared scripting-compiler-plugin code, so it also benefits any other current or future caller of `compileReplSnippet` that might pass a file-based source.

Also found and reverted an unrelated over-correction made mid-investigation: the daemon's actual `daemonCompilerClasspath` (verified by dumping the resolved configuration) contains no IntelliJ `analysis`/`intellij-core` jar at all, so the JDK 17 `testTask(javaLauncher = ...)` override added while chasing this bug was unnecessary once the real fix landed; removed it to keep the module on the repo's default test JDK.

## Addendum 2 (same day): `-script <file>` still evaluates -- moved snippet delivery off `ScriptEvaluationExtension` entirely

Follow-up review: *"if you make a test with a snippet that throws the exception, you likely get the exception in the daemon, rather than in the evaluator."* Verified by reproduction: a snippet whose *body* throws (e.g. `throw RuntimeException("boom")`) compiles fine, but `-script <path>` (like `-expression` before it) is delivered through `ScriptEvaluationExtension.eval()` -- the very same entry point `kotlinc script.kts` uses to *run* a script. `REPL_SNIPPET_COMPILATION_MODE` only short-circuits that entry point *before* it evaluates anything; it is a runtime flag check inside an evaluation-capable entry point, not a structural guarantee that evaluation can never happen there.

**Fix**: moved snippet delivery off `ScriptEvaluationExtension` (`-script`/`-expression`) entirely, onto the *regular* JVM source-root compile pipeline, which has no evaluation code path at all:

- `ScriptingProcessSourcesBeforeCompilingExtension.processSources` (the plugin extension already responsible for `-Xallow-any-scripts-in-source-roots` handling) now short-circuits when `REPL_SNIPPET_COMPILATION_MODE` is set: it calls the existing `compileReplSnippet` (`AbstractScriptEvaluationExtension.kt`) directly for each incoming source and returns `emptyList()`, so the snippet is never handed to the regular frontend/backend (which has no notion of REPL snippets/priors anyway).
- `DaemonReplSnippetCompiler` now delivers the snippet as a **plain source-root file** (a free/positional CLI argument, not `-script`/`-expression`), with three flags:
  - `-Xallow-any-scripts-in-source-roots` -- lets a `.kts` file be accepted on the regular source-root path at all.
  - `-Xuse-fir-lt=false` -- **the key fix**. `ScriptingProcessSourcesBeforeCompilingExtension` only ever runs on the *PSI-based* `KotlinCoreEnvironment.getSourceFiles()` source-collection path (`useLightTree = false`); the JVM pipeline's *other*, default (`useLightTree = true`) path (`collectSources`, light-tree/FIR) has no equivalent extension point. Without this flag the snippet was silently accepted and silently compiled into nothing -- no artifact, no diagnostic, and (misleadingly) exit code `0`. This flag is deprecated and scheduled for removal once light-tree mode becomes the compiler's only mode -- flagged as the one part of this design most likely to need revisiting.
  - `-Xallow-no-source-files` -- since the snippet is deliberately never handed to the regular frontend/backend, the pipeline's own visible source set is empty; without this flag that trips the JVM pipeline's hard "no source files" error.
- Added `testSnippetThatThrowsAtRuntimeFailsAtEvalNotCompile` (asserts the exception surfaces via `ScriptException` wrapping the thrown exception, from the in-process `$$eval` reflection call in `DaemonReplSnippetSession`, not as an "Error compiling" daemon-side failure) and `testSnippetWithCompileErrorFailsAtCompileNotEval` (asserts a genuine compile error is still reported distinctly, as an "Error compiling Kotlin snippet" `ScriptException`), to lock in both directions of this distinction.

### Diagnosis path (useful if this needs revisiting)

Root-caused via manual CLI reproduction against the daemon's resolved classpath: `-script <path>` alone reproduced the daemon-side-exception risk (confirmed by inspecting the pipeline: `JvmFrontendPipelinePhase`'s `ScriptEvaluationExtension` entry always evaluates once `REPL_SNIPPET_COMPILATION_MODE`'s short-circuit is bypassable in principle). Switching to a bare positional `.kts` argument (no `-script`) with only `-Xallow-any-scripts-in-source-roots` produced exit code `0` but **no artifact** -- tracing `JvmFrontendPipelinePhase.createEnvironmentAndSources` showed `configuration.useLightTree` (set from `-Xuse-fir-lt`, defaulting to `true`) picks between `collectSources` (light-tree, no plugin hook) and `kotlinCoreEnvironment.getSourceFiles()` (PSI, which does call `ProcessSourcesBeforeCompilingExtension`). Adding `-Xuse-fir-lt=false` alone produced the artifact but exit code `1` ("no source files", since our hook intentionally empties the source list); adding `-Xallow-no-source-files` alongside it produced exit code `0` **and** the artifact.

## Addendum 3 (same day): rebuilt on top of the stock REPL infrastructure instead of a from-scratch implementation

Follow-up review: the whole module was a **from-scratch** implementation that barely touched the existing K2 REPL infrastructure (`K2ReplCompiler`/`K2ReplEvaluator`/`KotlinJsr223JvmScriptEngineBase`) or its default-engine JSR-223 binding (`KotlinJsr223ScriptEngineImpl`) -- `DaemonReplSnippetCompiler` had nothing to do with `K2ReplCompiler`, and `DaemonReplSnippetSession` reimplemented (via raw reflection over a hand-rolled classloader) exactly what `K2ReplEvaluator` already does. Direction: substitute **only** the compiler (and, if needed, the state/result-extraction logic) on top of the existing infrastructure, extending the base infrastructure itself if required.

**What changed:**

- **`KotlinJsr223JvmScriptEngineBase<State>`** (`libraries/scripting/jvm-host`, shared by every JSR-223 engine built on the stock infra): its two abstract properties were loosened from the concrete `K2ReplCompiler`/`K2ReplEvaluator` types to their interfaces -- `replCompiler: ReplCompiler<CompiledSnippet>` / `replEvaluator: ReplEvaluator<CompiledSnippet, KJvmEvaluatedSnippet>`. This is the "base infrastructure change" the review anticipated might be needed: it's the *only* change to shared code this addendum required, and it's purely a widening (the existing `KotlinJsr223ScriptEngineImpl` override is unaffected since `K2ReplCompiler`/`K2ReplEvaluator` already implement those interfaces).
- **New `DaemonReplCompiler`** (`.../daemon/DaemonReplCompiler.kt`), a `ReplCompiler<CompiledSnippet>` that is the *only* substitution made: it wraps the existing `DaemonReplSnippetCompiler` transport unchanged, and decodes each successful wire artifact into a **real** `kotlin.script.experimental.jvm.impl.KJvmCompiledScript` -- its class bytes become an in-memory `KJvmCompiledModuleInMemoryImpl` (both public, `:kotlin-scripting-compiler`/`:kotlin-scripting-jvm` classes; keys re-suffixed with `.class` since the artifact's own map is keyed by bare JVM internal name), and its header (`snippetClassInternalName`, `resultPropertyName`) supplies the rest of the constructor arguments. A generic non-`kotlin.Unit` `KotlinType` placeholder is used for the result field's static type since the wire header doesn't carry it -- sufficient because `K2ReplEvaluator.evalSnippet` only ever special-cases the literal type name `"kotlin.Unit"`.
- **`KotlinJsr223DaemonScriptEngineImpl`** was rewritten to extend `KotlinJsr223JvmScriptEngineBase<DaemonReplState>` (mirroring `KotlinJsr223ScriptEngineImpl`/`K2ReplState` exactly) instead of implementing `AbstractScriptEngine`/`Compilable` directly. Its `DaemonReplState` holds a `DaemonReplCompiler` plus a completely **stock, unmodified** `K2ReplEvaluator` -- meaning cross-snippet classloader chaining (`ScriptEvaluationConfiguration.jvm.lastSnippetClassLoader`, set by `K2ReplEvaluator.eval` from the previous snippet's actual runtime classloader) now resolves cross-snippet references (`testCrossSnippetReference`) for free, with zero custom classloading code in this module.
- **Deleted `DaemonReplSnippetSession.kt`** entirely -- its reflection-based artifact-decode-and-replay logic (incremental classloader, `$$eval` reflection, result-field reflection) is now just what `K2ReplEvaluator` already does against the `KJvmCompiledScript` `DaemonReplCompiler` produces.
- Preserved the exact error-message shapes the existing tests assert on (`"Error compiling Kotlin snippet:\n..."` for compile failures, a bare `ScriptException(cause)` -- no "Error compiling" prefix -- for runtime failures at eval), so no test file changes were needed.

## Addendum 5 (2026-07-05, later same day): lazy, per-engine daemon connection instead of connect/release per compile

Follow-up review: *"You create the connection to the daemon on every compilation, and also wait for daemon to exit, which is not how the daemon is supposed to be used. You need to create a connection once per engine (lazily on the first compilation) and rely on engine disposal logic to clean the daemon up. [...] Also `daemonJvmOptions`, `daemonOptions` and `daemonLogOptions` should not be arbitrarily created in the `runDaemonCompile` (unless needed by the execution logic) but rather threaded right from the `KotlinJsr223DaemonScriptEngineFactory` constructor, and have null defaults there, in which cases the global defaults of the `newDaemonConnection` should be used."*

Before this addendum, `runDaemonCompile` called `KotlinCompilerRunnerUtils.newDaemonConnection(...)` and then `daemon.releaseCompileSession(sessionId)` (in a `finally`) on **every single snippet compile** -- with `shutdownDelayMilliseconds = 0` (the module's previous default), releasing the session left the daemon with zero active sessions, so it could shut itself down between every snippet, forcing the *next* compile to potentially wait for a fresh daemon spawn. This is exactly backwards from how a long-lived daemon client (e.g. the Gradle daemon client) is supposed to behave: lease a session once, hold it for the client's whole lifetime, and let disposal (not every individual request) release it.

**What changed (`DaemonReplCompiler.kt`):**

- Added a `@Volatile connection: CompileServiceSession?` field plus a `getOrCreateConnection(messageCollector)` method, double-checked-locked on a private `connectionLock`: the daemon connection is now created **once, lazily**, on the first `compileOnDaemon` call, and every subsequent call across the compiler's lifetime reuses the same leased session. `runDaemonCompile` no longer releases the session after each call.
- `DaemonReplCompiler` now implements `AutoCloseable`; `close()` releases the cached session exactly once (a no-op if no connection was ever created), leaving the daemon's own `daemonOptions.shutdownDelayMilliseconds`/idle-shutdown settings to decide when it actually exits -- appropriate since the daemon process may be shared with other, unrelated clients.
- Added a test-only `forceShutdownDaemon()` that calls `compileService.shutdown()` directly, mirroring `BaseDaemonSessionTest.stopDaemons()` (`compiler/daemon/daemon-tests`) rather than waiting out a real idle-shutdown delay between test runs.
- Replaced the old `daemonRunFilesPath: File` / `daemonLogsPath: File` / `shutdownDelayMilliseconds: Long` constructor parameters (which were used to hand-build a `DaemonOptions`/`DaemonLogOptions` inline inside `runDaemonCompile`, along with an unconditionally-synthesized `daemonJVMOptions`) with three nullable parameters -- `daemonJVMOptions: DaemonJVMOptions?`, `daemonOptions: DaemonOptions?`, `daemonLogOptions: DaemonLogOptions?` -- all defaulting to `null`. `getOrCreateConnection` falls back, on `null`, to exactly the same computation `newDaemonConnection`'s own no-arg overload performs internally (`configureDaemonOptions()`, `configureDaemonJVMOptions(inheritMemoryLimits = true, inheritOtherJvmOptions = false, inheritAdditionalProperties = true)`, plain `DaemonLogOptions()`), so passing `null` really does reproduce "the global defaults of `newDaemonConnection`". The run-files/log directories for whichever options end up in effect are still created via `Files.createDirectories`, since that step is genuinely needed by the execution logic regardless of who supplied the options.
- Threaded the same three nullable parameters through `KotlinJsr223DaemonScriptEngineImpl`'s and `KotlinJsr223DaemonScriptEngineFactory`'s constructors (replacing their own copies of the old path/delay parameters), and added `close()` / `forceShutdownDaemonForTests()` passthrough methods on the engine, mirroring `KotlinJsr223BtaScriptEngineImpl.close()`.
- `KotlinJsr223DaemonScriptEngineTest`: replaced the old `daemonRunFilesPath`/`daemonLogsPath`/`shutdownDelayMilliseconds` factory arguments with an explicit `DaemonOptions(runFilesPath = ..., shutdownDelayMilliseconds = 0)` / `DaemonLogOptions(logsPath = ...)` pair per test (still isolated per test via `@TempDir`), and added an `enginesToShutDown` list + `@AfterEach` that calls `forceShutdownDaemonForTests()` on every engine created during the test -- since the connection is no longer released between snippets, a test suite must now explicitly dispose of it rather than relying on it winding itself down on its own.

## Addendum 6 (2026-07-05, later same day): `kotlin.lazy` instead of manual locking; message collector as a reset-per-compile field, reported on success too

Follow-up review on addendum 5 itself: *"Why Volatile and manual handling? You should probably use Kotlin's `lazy` instead, and avoid manual locks too. And MessageCollector handling is strange. On the second snippet calculation you'll report a failure with the all messages, including ones from the previous compilation, while on the successful compilation, no messages (e.g. warnings) are taken from the message collector as well. You need to make message collector a field in the daemonReplCompiler, reset it before each compilation, and also report collected messages on the successful compilation too."*

Two independent issues, both in `DaemonReplCompiler.kt`:

1. **Reinventing `by lazy`**: the `@Volatile connection` field plus a hand-written double-checked-locked `getOrCreateConnection` was exactly what `kotlin.lazy`'s default (`SYNCHRONIZED`) thread-safety mode already does, just spelled out manually.
2. **Success never carried any messages**: `DaemonCompilationResult.Success` only ever carried the artifact bytes -- whatever the daemon reported for a *successful* compile (e.g. deprecation warnings, "jar not found" notices) was collected into `messageCollector` and then simply discarded, since only `Failure` read `messageCollector.messages`. Making `messageCollector` a shared field (rather than a fresh `CollectingMessageCollector()` per `compileOnDaemon` call, as it was) is *necessary* to give `connectionLazy`'s one-time connection-setup block a collector to report into, but doing so naively would introduce a real leak -- a later snippet's report would otherwise still carry an earlier snippet's stale messages -- unless it is explicitly reset before every single compile.

**What changed (`DaemonReplCompiler.kt`):**

- Replaced `@Volatile connection: CompileServiceSession?` + `connectionLock` + `getOrCreateConnection(messageCollector)` with a single `connectionLazy: Lazy<CompileServiceSession> = lazy { ... }` field (the same connection-setup logic, verbatim, as the lazy block) and a delegated `connection: CompileServiceSession by connectionLazy` property; `runDaemonCompile` now just reads `connection.compileService`/`connection.sessionId` directly. `close()`/`forceShutdownDaemon()` now guard with `connectionLazy.isInitialized()` (a public stdlib extension) instead of null-checking/nulling out a mutable field under a manual lock.
- `messageCollector` is now a single `private val` field (created once), read by both `connectionLazy`'s block and every `compileOnDaemon` call. `compileOnDaemon` now calls `messageCollector.clear()` immediately before `runDaemonCompile`, so a later snippet's report never carries an earlier snippet's stale messages.

## Addendum 8 (2026-07-05, later same day): "regular output" (`-d`) scheme, replacing the self-contained blob artifact

Follow-up review, prompted by noticing `repl-snippet-artifact-output` and its routing: *"why was it implemented via a separate option rather than the simple `-d` [...] I would assume that generating the regular output will widen the possible usage scenarios [...] Especially if the evaluation side would be able to read the contents via a regular classloader instead of a custom file-based deserializer. [...] please investigate why it was implemented as it is now, and whether the conversion [...] is possible and not overly complicated, and if yes - please implement it."*

**Why `repl-snippet-artifact-output` (a self-contained blob) exists at all**: it is the shape the Build Tools API's `CompileReplSnippetOperation` needs. `ReplSnippetCompilationResult.Success.artifact` is a **published, versioned** `kotlin-build-tools-api` type committed to a plain `ByteArray`, with no shared-filesystem assumption between the BTA client and whatever BTA implementation (in-process, daemon, ...) ends up serving the request -- so `SnippetArtifactCodec` base64-embeds every class file plus the header into one self-contained JSON blob. A same-machine CLI/daemon caller (this module) has no such constraint: caller and compiler already share a filesystem, exactly like a normal `kotlinc -d <dir>` invocation.

**Was the conversion possible, and worth it?** Yes, and it surfaced a real latent bug along the way:

- Added `SnippetArtifactDirectoryCodec` (`SnippetArtifact.kt`, `:kotlin-scripting-compiler`): writes/reads an artifact as a directory of plain, regular `.class` files plus a small out-of-band header file (fixed path `META-INF/kotlin-repl-snippet.header`, chosen so it can never collide with an emitted class). `compileReplSnippet` (`AbstractScriptEvaluationExtension.kt`) now branches on `-d`/`JVMConfigurationKeys.OUTPUT_DIRECTORY`: when set, it writes the "regular output" directory scheme instead of the `SnippetArtifactCodec` blob; priors are told apart the same way, by `File.isDirectory`. Both schemes now coexist -- BTA keeps using the blob scheme unchanged, since it still needs `ByteArray`-only, filesystem-independent transport.
- **Bug found while writing the new-scheme test** (`ScriptingCompilerPluginTest.testReplSnippetCompilationPipelineBranchRegularOutput`, which loads the produced classes through a plain `URLClassLoader`): `buildSnippetArtifactFromCompile` (`SnippetArtifactEmission.kt`) built `SnippetArtifact.classFiles` from `generationState.factory.asList()` unconditionally `removeSuffix(".class")`-ing every entry's relative path -- but that list also includes non-class outputs (a `META-INF/*.kotlin_module` file). Since that file's path doesn't end in `.class`, the suffix strip was a no-op, silently smuggling it into `classFiles` under a `.kotlin_module`-suffixed key. This was invisible on the blob path (`SnippetArtifactCodec` just base64-round-trips whatever bytes it's given, and nothing ever tried to load it as a class), but broke immediately on the new directory scheme: `SnippetArtifactDirectoryCodec.write` re-appended `.class` to every key, producing a bogus `META-INF/....kotlin_module.class` file that a real classloader then choked on (`ClassNotFoundException`). Fixed by filtering `factory.asList()` to `.class`-suffixed relative paths only, before building the map -- a real bug fix benefiting *all* callers (BTA and daemon), not scheme-specific.
- `:examples:scripting-jsr223-daemon`'s `DaemonReplCompiler` was migrated to the new scheme end-to-end, since it is exactly the "same-machine, shared-filesystem" caller the review had in mind: each snippet now compiles with `-d <snippet-output-dir>` instead of `repl-snippet-artifact-output`; `repl-snippet-prior-artifact` values are now prior snippets' own output directories (no bytes are read back and copied at all -- the directories are simply reused in place); `decodeCompiledSnippet` now builds a `KJvmCompiledScript` backed by a plain `KJvmCompiledModuleFromClassPath(listOf(outputDir))` classloader plus `SnippetArtifactDirectoryCodec.readHeader(outputDir)` for the wrapper-class-name/result-field metadata, instead of decoding a blob into an in-memory module. Since class files must stay loadable for as long as the classloader chain `K2ReplEvaluator` builds over them is in use (i.e. the engine's whole lifetime, not just the one `compile()` call), each snippet's `-d` output directory now lives under a new per-compiler `workRoot` temp directory that is only deleted in `close()`, rather than the previous per-compile temp dir that was deleted in a `finally` right after decoding.
- Removed `DaemonReplCompiler`'s previous `KJvmCompiledModuleInMemoryImpl`-based decode path entirely; it no longer needs `SnippetArtifactCodec`/`decodeHeader` at all.
