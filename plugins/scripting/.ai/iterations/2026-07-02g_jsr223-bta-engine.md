# JSR-223 K2 bindings / stateless remote compilation — reusable BTA-backed `ScriptEngine` — 2026-07-02g

## Overview

Per explicit direction: with JSR-223 K2 bindings (Option D) essentially complete and the stateless remote REPL snippet compilation transport (Q5d, `CompileReplSnippetOperation`) fully landed, the next concrete deliverable requested is **one more `KotlinJsr223JvmScriptEngineFactoryBase` implementation** that drives compilation entirely over the Build Tools API, plus tests exercising it by direct instantiation (no separate `javax.script` service-registration module needed yet).

## Workstream / Issue

Migration-plan step 1 (JSR-223 K2 bindings) / Q5 (stateless remote compilation, specifically Q5d's transport). This is a new consumer built on top of already-landed work, not a fix.

## Decisions made up front (via clarifying questions)

1. **Module placement**: new dedicated module (`libraries/scripting/jsr223-bta`, project `:kotlin-scripting-jsr223-bta`) rather than adding the BTA dependency into the core `jvm-host` module.
2. **Bindings scope**: deferred for this first cut — no `ScriptContext`/`Bindings` implicit receiver support; `$$eval` is invoked with no arguments.
3. **Test execution style**: tests drive a real Kotlin compile daemon (`ExecutionPolicy.WithDaemon`), mirroring `ReplSnippetCompilationTest` (`:kotlin-build-tools-api-tests`), not a faked/in-process transport.

## What was built

- **`BtaReplSnippetSession`** (`libraries/scripting/jsr223-bta/src/.../bta/BtaReplSnippetSession.kt`): decodes a `SnippetArtifact` (via the public `SnippetArtifactCodec`/`decodeHeader()`), defines its classes onto a shared classloader (incrementally, one artifact per call), invokes `$$eval` reflectively (hardcoded `"$$eval"` literal per `AGENT_INSTRUCTIONS.md`'s "stable, don't rename/shadow" guidance, to avoid pulling `kotlin-compiler` into this module just for a `Name`-typed constant), and returns the captured result field's value (or `null` for a declaration-only snippet). Deliberately a small from-scratch reimplementation, not a reuse of the `internal`-to-`:kotlin-scripting-compiler` `SnippetArtifactEvaluator`.
- **`KotlinJsr223BtaScriptEngineImpl`** (`.../bta/KotlinJsr223BtaScriptEngineImpl.kt`): a `javax.script.AbstractScriptEngine` + `Compilable` implementation. Each `eval`/`compile` call builds a `CompileReplSnippetOperation` (prior artifacts + new source + a synthetic per-call snippet name), executes it via `KotlinToolchains.BuildSession.executeOperation(op, ExecutionPolicy.WithDaemon)`, and on `Success` hands the artifact to a `BtaReplSnippetSession` to run. On `Failure`, throws `ScriptException` with the rendered diagnostics. One engine instance == one REPL session (`priorArtifacts` accumulates).
- **`KotlinJsr223BtaScriptEngineFactory`** (`.../bta/KotlinJsr223BtaScriptEngineFactory.kt`): the requested `KotlinJsr223JvmScriptEngineFactoryBase` subclass; takes an implementation classpath (for `KotlinToolchains.loadImplementation`), an additional-classpath list (for the compiled snippets, e.g. stdlib), and a daemon-policy customizer. **Not** registered as a `javax.script.ScriptEngineFactory` service, per the issue's explicit ask ("we do not need a separate module... but rather an implementation that could be reused in such a module... instantiate it manually rather than via `javax.script`").
- **`KotlinJsr223BtaScriptEngineTest`** (`libraries/scripting/jsr223-bta/test/.../bta/test/KotlinJsr223BtaScriptEngineTest.kt`): 4 tests — simple arithmetic eval, cross-snippet reference (`val x = 10` then `x * 2`), separate `compile()`-then-`eval()`, and a declaration-only snippet returning `null`. Constructs the factory directly (manual instantiation, as requested) and drives a real daemon via `ExecutionPolicy.WithDaemon`, with `DAEMON_RUN_DIR_PATH`/`LOGS_PATH` pointed at a JUnit5 `@TempDir` and `SHUTDOWN_DELAY_MILLIS = 0` for fast, isolated teardown.
- **`libraries/scripting/jsr223-bta/build.gradle.kts`**: `api(":kotlin-scripting-jvm-host-unshaded")` (the plain, unshaded base-class module — matching `jsr223-test`'s convention, not the embeddable/shaded `:kotlin-scripting-jvm-host`) + `api(":compiler:build-tools:kotlin-build-tools-api")` + `implementation(":kotlin-scripting-compiler")` (only for the compiler-independent `SnippetArtifact`/`SnippetArtifactCodec` types) + `testRuntimeOnly(":kotlin-compiler")` (needed because `jvm-host-unshaded`'s own classes reference compiler-core types like `KotlinCompilerVersion`). A separate `btaImplClasspath` configuration (`kotlin-build-tools-compat` + `kotlin-build-tools-impl` + `kotlin-build-tools-cri-impl`, mirroring `kotlin-build-tools-api-tests`'s `buildToolsApiImpl` exactly) is resolved and handed to the test JVM via a system property, so `KotlinToolchains.loadImplementation` loads the implementation from an explicit, self-contained classpath the way a real embedder would.
- Registered the new module in `settings.gradle.kts` (include + `projectDir` mapping) and added `:kotlin-scripting-jsr223-bta` to the `notCacheableTestProjects` exemption list in `repo/gradle-build-conventions/buildsrc-compat/src/main/kotlin/common-configuration.gradle.kts` (same exemption `:kotlin-scripting-jsr223-test`/`:kotlin-scripting-jvm-host-test` already use, required by the project's test-caching convention for modules without the `test-inputs-check(-v2)` plugin).

## Bugs hit and fixed along the way

1. **Destructuring syntax**: initially wrote `for ((k, v) in map)`-equivalent using the square-bracket destructuring syntax seen in `SnippetArtifact.kt`/`SnippetArtifactEvaluator.kt` (`for ([k, v] in ...)`) — that syntax is only available under a language feature/flag those core modules opt into; this module doesn't, so it was rewritten as a plain `Map.Entry` iteration (`for (entry in map) { entry.key; entry.value }`).
2. **Duplicate compiler on the daemon classpath**: an initial `btaImplClasspath` of `kotlin-build-tools-impl` + `:kotlin-compiler` broke the daemon at startup — `kotlin-build-tools-impl` already transitively brings in its own compiler/scripting dependencies (compat + cri-impl + compiler-runner + compiler-embeddable, etc.); adding `:kotlin-compiler` directly put a second, conflicting compiler copy on the classpath. Fixed by dropping the direct `:kotlin-compiler` addition and instead listing exactly `kotlin-build-tools-compat` + `kotlin-build-tools-impl` + `kotlin-build-tools-cri-impl`, mirroring `kotlin-build-tools-api-tests`'s `buildToolsApiImpl` set precisely.
3. **The real blocker — stale/partial `kotlin-build-tools-impl` jar**: even with the correct dependency set, the daemon log (captured by pointing `ExecutionPolicy.WithDaemon.LOGS_PATH` at a stable temp dir instead of the default) showed `exception on loading scripting plugin: java.lang.ClassNotFoundException: org.jetbrains.kotlin.scripting.compiler.plugin.ScriptingK2CompilerPluginRegistrar` — the **unrelocated** class name, even though `CompileReplSnippetOperationImpl.createScriptingPluginServicesJar`'s own KDoc says the registrar/plugin classes must come from the *relocated* copy embedded in the shaded `kotlin-build-tools-impl` jar. Running `:compiler:build-tools:kotlin-build-tools-api-tests:testCompilerPlugins --tests "*ReplSnippetCompilationTest*"` (the reference test) once, standalone, passed cleanly — and afterwards, re-running this module's own tests (with no code changes) also passed. Conclusion: the `kotlin-build-tools-impl-*.jar` on disk had been built by an earlier, unrelated task graph in a form that didn't include the embedded/relocated scripting classes (a Gradle up-to-date/task-selection artifact of this monorepo's build, not a bug in this module's wiring); once a task that genuinely needs the fully-embedded jar ran, the shared jar file was rebuilt correctly and both consumers picked it up. No production code change was needed for this; documented here (and cross-referenced from the target doc) so it isn't mistaken for a real classpath-wiring bug in a future session.

## Verification

## Key Learnings

- When a Build-Tools-API-backed daemon operation fails with an unhelpful, empty-diagnostics `Failure` (or a silently-swallowed exception), point `ExecutionPolicy.WithDaemon.LOGS_PATH` (plus `DAEMON_RUN_DIR_PATH`) at a stable, inspectable directory instead of the default temp location — the daemon's own log file captures the real underlying compiler/plugin-loading exception (with the real class name/stack trace) that the structured `ReplSnippetCompilationResult.Failure` surface does not.
- A dependency set that looks structurally correct (right modules, right names) can still resolve to a *stale build artifact* of one of those modules in a large multi-project Gradle build; when a very specific, precisely-worded runtime error (like an unrelocated class name that "shouldn't" be possible per the producing code's own contract) doesn't match any plausible wiring mistake, running the *reference/known-good* consumer of the exact same dependency once (forcing a fresh, complete build of the shared artifact) is a fast way to test that hypothesis before spending more time re-deriving Gradle variant-resolution theories.
- This module intentionally reimplements a small amount of internal-module logic (`BtaReplSnippetSession` vs. `SnippetArtifactEvaluator`) rather than reaching for `internal` visibility across module boundaries — consistent with how `BtaReplSnippetSession`'s own KDoc documents the tradeoff; only the *public* `SnippetArtifactCodec`/`SnippetArtifactHeader` wire types are shared.
